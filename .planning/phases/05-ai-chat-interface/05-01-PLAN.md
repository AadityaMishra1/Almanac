  <action>
Install the three new dependencies:
```
npm install ai @ai-sdk/anthropic chrono-node
```

Create `types/chat.ts` with the following type definitions:

1. `ChatMessage` - extends Vercel AI SDK message type with optional metadata:
   - `id: string`
   - `role: 'user' | 'assistant' | 'system' | 'tool'`
   - `content: string`
   - `toolInvocations?: ToolInvocation[]` (from 'ai' package)

2. `ToolResult` - discriminated union for tool execution results:
   - Success: `{ ok: true; requiresConfirmation: boolean; data: unknown }`
   - Error: `{ ok: false; error: string }`

3. `ConfirmationPayload` - what the UI receives for confirmation dialogs:
   - `type: 'modify' | 'delete' | 'create' | 'bulk-delete'`
   - `description: string` (human-readable summary)
   - `changes?: { before: EventSnapshot; after: EventSnapshot }` (for modify)
   - `items?: EventSnapshot[]` (for bulk operations)
   - `conflicts?: ConflictWarning[]` (time overlap warnings)

4. `EventSnapshot` - serializable event state for diffs:
   - `id: string`
   - `title: string`
   - `date: string`
   - `time: string | null`
   - `type: string`
   - `courseName: string`

5. `ConflictWarning`:
   - `eventId: string`
   - `eventTitle: string`
   - `message: string`

6. `CommandRecord` - for undo history persistence:
   - `id: string`
   - `type: 'modify' | 'delete' | 'create'`
   - `description: string`
   - `beforeState: string` (JSON serialized EventSnapshot or null for create)
   - `afterState: string` (JSON serialized EventSnapshot or null for delete)
   - `eventId: string`
   - `timestamp: Date`
   - `undone: boolean`

Export all types as named exports.
  </action>

Run `npx tsc --noEmit` to confirm types compile without errors. Verify `ai` and `@ai-sdk/anthropic` and `chrono-node` appear in package.json dependencies.
  </verify>

**lib/ai/date-parser.ts:**
Create a chrono-node wrapper with academic calendar integration:

1. Import `chrono-node` (casual mode) and academic calendar dates from `@/lib/calendar/ncsu-academic-calendar.ts`
2. Create custom chrono instance with academic refiners:
   - "finals week" -> maps to the finals week date range from ncsu-academic-calendar
   - "spring break" -> maps to spring break dates from ncsu-academic-calendar
   - Validate parsed dates are within semester bounds (warn if outside)
3. Export `parseUserDate(input: string, referenceDate?: Date): { date: Date; formatted: string } | null`
   - Uses casual chrono parsing
   - Returns null if unparseable
   - `formatted` is human-readable string like "Friday, March 15, 2026"
4. Export `formatDateForDisplay(date: Date): string` using date-fns format
5. Export `formatDateForDb(date: Date): string` returning YYYY-MM-DD ISO string
6. Export `parseTimeFromInput(input: string): string | null` returning HH:MM format or null

**lib/ai/prompts.ts:**
Create the system prompt builder:

1. Export `buildSystemPrompt(context: { events: EventSnapshot[]; courses: { code: string; name: string }[]; currentDate: string }): string`
2. The system prompt must include (per CONTEXT.md decisions):
   - Personality: helpful and informative, explain context, offer insights
   - Safety: ONLY modify events with source='almanac', never external Google Calendar events
   - Ambiguity: ask clarifying questions when command is unclear
   - Date context: current date, semester bounds for date interpretation
   - Event context: list of current events and courses (injected dynamically)
   - Tool usage: use tools for all event operations, never claim to do something without calling a tool
   - Conflict awareness: check for time overlaps before modifying events and warn user
   - Source distinction: reference external Google Calendar events but clarify they're read-only
   - Bulk operations: for bulk operations, always list all matching events for confirmation
3. Keep prompt under 2000 tokens to leave room for conversation

**lib/ai/tools.ts:**
Define AI SDK tools with Zod schemas wrapping existing server actions:

1. `modifyEventTool` - tool() with:
   - description: "Modify an existing Almanac event's title, date, time, or type"
   - inputSchema: z.object with eventId (string), optional newTitle, newDate, newTime, newType
   - execute: Look up event by ID, check source === 'almanac', build ConfirmationPayload with before/after diff, return `{ ok: true, requiresConfirmation: true, confirmation: ConfirmationPayload }`. Do NOT execute the update yet -- confirmation comes from UI.

2. `deleteEventTool` - tool() with:
   - description: "Delete an Almanac event"
   - inputSchema: z.object with eventId (string), reason (optional string)
   - execute: Look up event, check source === 'almanac', return confirmation payload

3. `createEventTool` - tool() with:
   - description: "Create a new Almanac event"
   - inputSchema: z.object with title, date, time (optional), type, courseCode
   - execute: Validate course exists, parse date with parseUserDate, return confirmation payload

4. `queryEventsTool` - tool() with:
   - description: "Search events by title, date range, course, or type. Use this to find events before modifying them."
   - inputSchema: z.object with optional query (string), courseCode, dateRange, type
   - execute: Query database using getEvents, return matching events. NO confirmation needed (read-only).

5. `bulkDeleteTool` - tool() with:
   - description: "Delete multiple Almanac events matching criteria"
   - inputSchema: z.object with filter criteria (type, courseCode, dateRange)
   - execute: Find matching Almanac events, return confirmation payload with items array

All tools use `prisma` for database access (import from `@/lib/db`). Tools that modify data return `requiresConfirmation: true` and the proposed changes. The actual mutation happens AFTER user confirms (handled in Plan 03).

Use date-parser's `parseUserDate` within tools for natural language date inputs. Import `findConflicts` from `@/lib/calendar/conflict-detection.ts` for conflict warnings in modify/create tools.

IMPORTANT: Do NOT import from `app/server-actions/` directly in tools -- instead import `prisma` from `@/lib/db` and query directly. Server actions have `"use server"` directive and cannot be called from API routes. The tools run server-side in the API route context.
