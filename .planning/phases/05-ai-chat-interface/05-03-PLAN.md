**app/api/chat/execute/route.ts:**
Create a POST endpoint that executes confirmed event operations. This is called by the confirmation UI when user clicks "Approve".

Request body schema (use Zod validation):
```
{
  action: 'modify' | 'delete' | 'create' | 'bulk-delete',
  // For modify:
  eventId?: string,
  updates?: { title?, date?, time?, type? },
  // For delete:
  eventId?: string,
  // For create:
  newEvent?: { title, date, time?, type, courseId },
  // For bulk-delete:
  eventIds?: string[],
  // For undo tracking (all actions):
  beforeState?: EventSnapshot | null,
  afterState?: EventSnapshot | null,
}
```

Implementation:
1. Parse and validate request body with Zod
2. Switch on `action`:
   - `modify`: Use prisma to update event (check source === 'ALMANAC' first). If event has googleEventId, also update Google Calendar via getCalendarClient (get session for access token).
   - `delete`: Use prisma to delete event (check source === 'ALMANAC'). If event has googleEventId, delete from Google Calendar too (graceful -- don't block on failure, same pattern as deleteGoogleCalendarEvent in calendar.ts).
   - `create`: Use prisma to create event with source='ALMANAC', editable=true. Look up courseId from courseCode if needed.
   - `bulk-delete`: Loop through eventIds, delete each (Almanac source only). Try-catch per event so one failure doesn't block others.
3. Return `{ ok: true, result: { ... } }` or `{ ok: false, error: string }`
4. Also return a `commandRecord` in the response that captures before/after state for undo (using the beforeState/afterState from request body). This will be stored client-side temporarily and persisted to DB in Plan 04.

For Google Calendar sync on modify/delete:
- Import `getServerSession` from `next-auth` and `authOptions` from `@/lib/auth`
- Import `getCalendarClient` from `@/lib/google`
- If session has accessToken, attempt Google Calendar update/delete
- If no session or GCal fails, still succeed locally (graceful degradation pattern from Phase 4)

**Update components/chat/ChatMessages.tsx:**

Modify the message rendering to detect tool invocation results that require confirmation and render the appropriate confirmation component instead of raw JSON.

1. Import CommandConfirmation and BulkConfirmation
2. Add a new prop: `onOperationComplete: () => void` -- this callback is called after any successful execute to trigger calendar refresh
3. For each message, check if it has `toolInvocations` (from Vercel AI SDK Message type)
4. For each tool invocation with a result:
   - Parse the result object
   - If result has `requiresConfirmation: true`:
     - Check `confirmation.type`:
       - `'modify'`, `'delete'`, `'create'` -> render `<CommandConfirmation />`
       - `'bulk-delete'` -> render `<BulkConfirmation />`
     - Track confirmation state per tool call ID: `pendingConfirmations` map in component state
     - On approve: call the execute endpoint, then update state to show "Executed successfully" or error, then call `onOperationComplete()`
     - On reject: update state to show "Cancelled by user"
   - If result does NOT have `requiresConfirmation` (e.g., queryEventsTool results):
     - Render a compact formatted card showing the query results (event list with title, date, type)
     - Not raw JSON -- format as a clean list

5. After successful execution:
   - Replace the confirmation UI with a success message: green checkmark + "Done: {description}"
   - Call `onOperationComplete()` to trigger calendar refresh

6. After rejected:
   - Replace the confirmation UI with a muted message: "Cancelled"

State management approach:
- Use a `Map<string, 'pending' | 'approved' | 'rejected' | 'executing' | 'done' | 'error'>` keyed by tool call ID
- `useState` for the map, update via setter
- Pass `isExecuting` prop based on state being 'executing'

**Update components/chat/ChatWidget.tsx:**

1. Import `useRouter` from `next/navigation`
2. Create a stable callback: `const handleOperationComplete = useCallback(() => { router.refresh(); }, [router])`
3. Pass `onOperationComplete={handleOperationComplete}` to `<ChatMessages />`
4. This single callback pattern ensures ChatMessages never needs to import useRouter itself -- it just calls the callback prop after any successful execute

The execute fetch call pattern (inside ChatMessages approve handler):
```typescript
const response = await fetch('/api/chat/execute', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    action: confirmation.type,
    eventId: confirmation.changes?.before?.id,
    updates: { /* from confirmation.changes.after */ },
    beforeState: confirmation.changes?.before,
    afterState: confirmation.changes?.after,
    // or for bulk: eventIds: selectedIds
  }),
});
const result = await response.json();
if (result.ok) {
  // Update confirmation state to 'done'
  onOperationComplete(); // triggers router.refresh() in parent
}
```

Error handling:
- If execute returns `ok: false`, show error message inline below the confirmation
- If network error, show "Failed to execute. Please try again." with a retry button
